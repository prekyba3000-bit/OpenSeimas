# Filling the empty tables — audit, one incident, and a feasibility note

2026-09-06. The task was: fill the tables the data ledger showed as empty,
since several of them will be essential once populated. Recon before code,
per §1.8. What recon found changed the task.

## The incident: an AI-generated risk label was already live in the repo

While tracing what could fill `assets`/`interests`, `dashboard/src/components/
WikiPanel.tsx` turned up — wired into every MP profile, fetching `/wikis/
{mp_id}.md`. That file is meant to be generated by an agent task
(`docs/archive/generate_mp_wikis.md`) that researches a member from database
fields and a web search, then writes a report ending in a **Risk Level: Low /
Medium / High / Critical**.

That task had already run. `dashboard/public/wikis/index.json` — committed to
git since the repository's first commit, in a **public** GitHub repo (verified:
`isPrivate: false`) — assigned five named members a risk level, four of them
"High". A second, earlier attempt (`docs/wiki-archive/`) had produced plain
biographical pages for a few more members, plus its own note recording that a
"flag MPs below an integrity threshold" pass had failed to run — evidence the
mechanism was attempted more than once.

The individual report files were never committed to `dashboard/public/`, so
the deployed Vercel site 404'd on them and showed a harmless empty state — the
live site was not currently displaying a risk label to a visitor. But
`index.json` **was** committed to the exact path the frontend serves, and the
whole feature would have shown a "Risk Level" verdict on a real profile the
moment anyone regenerated and committed the missing files. It was one
`git add` away from live, and had been for the project's entire history.

This is the same failure the corrections log already names twice —
„herojų ir piktadarių" (heroes-villains) and „Gėdos siena" — a computed
judgement about a named person, published as fact. It reached further than
either: a static JSON asset, which is invisible to a grep over source code.
`dashboard/src/i18n/noVerdictsInStaticData.test.ts` exists specifically to
catch exactly this class of defect — built after the „Gėdos siena" incident —
and it was already running while this file existed. It did not catch it:
`risk_level` matched none of its forbidden-key patterns (`rank`, `unearned`,
`top\d+_`, `shame`, `score$`, `grade$`). A guard with a fixed vocabulary only
catches defects shaped like the one it was written for.

### What was removed

- `dashboard/src/components/WikiPanel.tsx`, `services/wiki.ts`,
  `services/wiki.test.ts`, and its render call site + the now-empty
  "Biografija" tab in `MpProfileView.tsx`.
- `dashboard/public/wikis/` — the committed `index.json` and five locally
  generated report files that were never committed.
- `docs/wiki-archive/` in full — both the risk-labelled set and the earlier
  biographical/orphans set. All of it names real people from unreviewed LLM
  output; none of it belongs in a published repository regardless of whether
  the risk-level field is present.
- The `wiki` block in `dashboard/src/i18n/lt.ts`, unused once the component is
  gone.

### What was kept

`docs/archive/generate_mp_wikis.md` and `docs/history/merger_plan_and_
cursor_prompts.md` — process documentation of how the feature was specified
and built. Neither names a specific member with a verdict; both are the kind
of record the methodology page already keeps on purpose („Formulę paliekame
čia, kad jos pašalinimas iš puslapių nebūtų tas pat, kas jos nuslėpimas" —
same logic applied to a retired task spec as to a retired formula).

### What was fixed in the guard

`noVerdictsInStaticData.test.ts` now also matches `risk_level` and
`integrity_score`. Its own self-check — "a guard that scans no files always
passes" — asserted `files.length > 0` against the real `public/` directory,
which is precisely the coupling that let this slip through: once the
offending file is gone, that assertion cannot tell a clean directory from a
guard that was never wired up correctly. It now feeds the matcher functions a
synthetic case shaped like the one that shipped, and separately proves the
directory walk itself works against a disposable temp directory — neither
check depends on this repository happening to ship a particular file.

### What was not done

**Git history is not rewritten.** `index.json`'s content is still reachable
via `git log` on GitHub, and has been public since the first commit; anyone
who already cloned or viewed it has had access regardless of what the current
tree holds. Rewriting history is a destructive, shared-state operation —
it can break other clones, and does not retroactively un-publish something
that has already been public — and is not mine to do unilaterally. If the
human wants to pursue it (contacting GitHub, a history rewrite plus force-push
with a warning to any other clone), that is a decision for them, not something
executed as part of this fix.

**The four named members are not identified here or in the corrections
entry.** Repeating the specific rating in the document that corrects it would
publish the exact thing being corrected, under the platform's own authority.
The corrections entry (`ai-wiki-risk-labels`) describes the mechanism, not
the instance.

## The rest of the original question: which empty tables can be filled

### Filled today, safely — no action needed

**`legislation_topics`** — already ran. The nightly `daily_sync.sh` includes
both my last session's `ingest_legislation` fix and the pre-existing
`tag_topics` step; the two composed correctly on their own schedule. 1,098
topic tags across 975 of 1,683 bills, deterministic keyword matching, no
score involved. A manual re-run confirmed it idempotent (0 changes — nothing
new to tag).

### Real source found, but gated behind a feasibility note (§ W3 rule)

**`assets` and `interests`.** The current `SourcesView` copy says these are
uncollectable because VTEK's private-interest register blocks automated
reading. That is true of VTEK — but **it is not the only source**, and this
project already has schema and code assuming a different one:

- `rezultatai.vrk.lt` publishes, for every 2024 Seimas candidate, an asset/
  income declaration page (`KandidatasTurtoPajDekl_rkndId-*`) and a **separate
  private-interest declaration page** (`KandidatasPrivInterDekl_rkndId-*`) —
  legally required campaign-transparency filings, not the ongoing VTEK
  register. Verified live: both return real, structured content (employer,
  organisation code, role, dates — even a spouse's employer) for real
  candidate IDs, on both domains' `robots.txt` disallows nothing relevant.
- `migrations/012_interests_org_code.sql` and `013_procurement_contracts.sql`
  already anticipate this exact shape (`organization_code`,
  `parsed_organization_name`) and a matching `procurement_contracts` /
  `mp_supplier_links` pipeline (`pipeline/ingest_cvp_is_procurement.py`,
  well-documented, idempotent) — built, never run, because its input
  (`interests.organization_code`) has never existed.
- The actual blocker is upstream of either table: **zero of 148 politicians
  have `vrk_candidate_id` populated.** `pipeline/link_vrk.py` exists to fill
  it, fetches a live source (verified, 1,740 candidate links), but matches by
  **normalised name only — no constituency or party disambiguation.** Given
  common Lithuanian surnames and that a wrong match here would attach one
  real person's income, loans, and family employer relationships to a
  different named person, this is not safe to run as written.
- `pipeline/ingest_assets.py` additionally targets a table, `mp_assets`, that
  does not exist (`schema.sql` has only `assets`) — it would fail immediately
  if invoked, and separately has no interests-declaration counterpart at all.

**Not built now**, per the standing rule already in this repository's own
notes: declared-interest and asset data "most invites verdict-shaped
presentation" and needs a feasibility note before any ingest code — a rule
this session's own finding makes concrete rather than hypothetical. The note
needs to cover, before any data arrives:
1. A disambiguation fix for `link_vrk.py` (constituency + party cross-check
   against `ingest_vrk_results.py`'s existing apygarda data, at minimum).
2. What the surface does with a real net-worth figure next to a name —
   evidence only (the declared figure, dated, sourced, with the declaration
   linked), never a computed "wealth score," "conflict score," or ranking.
   The `mp_supplier_links` view already produced by migration 013 is
   fact-shaped (org code, role, contract, amount) rather than score-shaped,
   which is the right template — but the phantom-network *edge label itself*
   ("phantom_network") is loaded language worth revisiting in the same pass.
3. What happens when a declaration cannot be linked, is incomplete, or a
   candidate never won a seat — every gap needs the unknown-renders-as-unknown
   treatment, not a silent zero.

### STOP — verdict-shaped by construction, not by accident

**`vote_geometry` / `mp_vote_geometry`.** `pipeline/compute_vote_geometry.py`
is schema-compatible and needs no new data — it computes a per-MP "defection
from a statistically anomalous vote" count and a max deviation-sigma directly
from `mp_votes`, which is already fully populated. It is genuinely one command
away from working. It is not run. Populating this table for the first time
would switch a live per-MP anomaly flag on for every member, with no design
review, no evidence-first framing, and no human sign-off — precisely what
charter §4.6 requires stopping and recording rather than executing. The
`faction_alignment` precedent (`p4-legislative-recon.md`) is the template: the
raw anomalous votes a reader can open and judge for themselves need to exist
on a surface *before* any aggregate sigma/flag does, not after.

**`benford_analyses`, and the never-wired legacy engines.** `skaidrumas/
analysis/{chrono_forensics,loyalty_graph,benford_engine,phantom_network}.py`
are a fully separate, disconnected subsystem — a different storage layer
(`skaidrumas/storage/db.py`, SQLAlchemy models `MP`/`ConflictAlert`/`Amendment`
/`AmendmentProfile`) that the current backend (`backend/hero_engine.py`,
`routes_forensics.py`) never imports; confirmed by grep, the only overlap is
shared English words in route/dict names. Their own docstrings describe
"Engine 03: Factional Betrayal Detection... surface emerging cross-party
shadow coalitions" and "Engine 01: Amendment Temporal Fingerprinting... detect
coordinated multi-MP bursts from external drafting sources." This reads as
tabloid-shaped by design, from an earlier phase of the project that predates
the current charter — consistent with `memory-bank/activeContext.md`
describing an "OpenPlanter" pipeline and hero XP/level system already
superseded by this session's and prior sessions' corrections. **Recommend:
do not revive.** If kept at all, keep as historical record only, matching how
the wiki generator's spec was kept; reconnecting it to real data is a
redesign decision for the human, not a backfill task.

### Correctly empty, no action

`amendment_profiles`, `mp_amendment_counts` — superseded by the
`amendments_proposed_count` proxy already in use (established in the P4
recon). `mp_replies`, `recommendations`, `recommendation_feedback`,
`quarantine_rows`, `summary_revisions` — not ingest targets; they fill through
member replies, the dq-check runner, or a human-approved publish, respectively.
None of these are gaps to backfill.
