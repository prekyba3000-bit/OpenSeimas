# Evaluation SECA-08 — the platform stops holding reporter e-mail

2026-11-26. Branch `fix/eval-stage1`.

## Decision

The human chose to remove the optional e-mail box from the correction form
rather than keep it with a privacy notice, retention rule and erasure route.
Reasons: only 1 of 24 production reports ever left an address; no product
surface ever read it (no admin route selected it); every report's outcome is
already published in the corrections log; and a complete GDPR Art. 13 notice
would need a controller legal name that does not exist yet. Holding nothing is
the whole fix: no notice, retention job, erasure path or US-transfer basis is
needed for data the platform does not collect.

## Recon

- `corrections.reporter_email` (migration 017) was the platform's only
  first-party personal data. Production on 2026-11-26: 24 rows, all `resolved`,
  1 with an address (read as counts only; the address was never displayed).
- Writers: `POST /api/trust/corrections` and `CorrectionForm.tsx`. Readers: none.
- Copies: local dumps keep the newest 30 (daily); offsite keeps 4 weekly
  archives (`last-success-offsite` 2026-11-24). Both age the address out within
  about five weeks of the column drop.

## What changed

- **Form:** the e-mail field and its note are gone. No new UI copy.
- **API:** `CorrectionIn` no longer declares `reporter_email`; pydantic drops the
  key if an old cached page sends it, and the INSERT no longer names the column.
- **Migration 058:** `DROP COLUMN reporter_email` (erasing the one address), plus
  a published corrections entry `reporter-email-retention` naming the gap.
- **Deploy order:** backend first (it must stop inserting the column), then 058.
  The old frontend against the new backend, and the new frontend against the
  old backend, both work.

## Tests

- `test_no_table_holds_an_email_column` (real Postgres): pattern guard over all
  public columns named like e-mail / „paštas". Proven to fail before 058
  (`['corrections.reporter_email']`) and pass after.
- `test_submission_with_a_reporter_email_stores_the_report_only` (real Postgres)
  and `test_submit_correction_drops_a_reporter_email_from_an_old_page` (mock):
  an old page's address reaches neither SQL nor parameters nor the row.
- Dashboard: the form renders no e-mail input or label and sends no
  `reporter_email` key.
- Fresh Postgres: 57 → 58 migrations, second run `0 applied, 58 already
  up-to-date`; a pre-058 row with an address survives the drop. Backend **542
  passed**; form + log tests 12 passed; `tsc` no errors outside vendored `ui/`.
